# text2me — правила дизайна и интерфейсного поведения

**Статус:** проектный стандарт для новых изменений и поэтапной унификации существующих страниц.  
**Базовый режим:** документ в центре; инструменты и дополнительные действия открываются по запросу.  
**Основной язык:** русский. **Основная аудитория:** граждане, ИП, организации и специалисты по документам.

## 1. Источники и применимость

Использовать как проверяемые ориентиры, не как заявление о сертификации сайта:

- [U.S. Web Design System — Button](https://designsystem.digital.gov/components/button/)
- [U.S. Web Design System — Button group](https://designsystem.digital.gov/components/button-group/)
- [W3C — WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- [GOV.UK Design System — Text input](https://design-system.service.gov.uk/components/text-input/)
- [Microsoft Fluent 2 — Button usage](https://fluent2.microsoft.design/components/web/react/core/button/usage)
- [Microsoft Fluent 2 — Accessibility](https://fluent2.microsoft.design/accessibility)
- [Adobe Acrobat — editing overview](https://helpx.adobe.com/acrobat/web/edit-pdfs/edit-text-images-and-objects/editing-pdfs-overview.html)

USWDS рекомендует не объединять несвязанные действия в одну группу и не перегружать пользователя вариантами. GOV.UK требует явные подписи полей и ширину, соответствующую содержимому. Fluent 2 рекомендует визуально выделять главное действие и не придавать второстепенным кнопкам одинаковый вес.

## 2. Архитектура интерфейса — режим B

1. **Документ или текущая задача — главный объект страницы.** На странице редактирования документ занимает основную рабочую область.
2. **Инструменты по запросу.** Редко используемые инструменты, свойства и справочные панели открываются по явному действию и не отнимают постоянное место у документа.
3. **Единая шапка и навигация.** Название text2me, основные разделы, поиск и указание текущего пути должны иметь единый порядок и поведение на всех страницах.
4. **Контекст прежде всего.** На странице документа показывать действия, применимые к этому документу; в календаре — действия с событиями; в деле — действия со связанными документами, контактами и задачами.
5. **Не имитировать несуществующие функции.** Если действие ещё не реализовано, не оформлять его как рабочее. Сообщать статус и предлагать существующий следующий шаг.
6. **Состояния обязательны.** Для каждого асинхронного или интерактивного действия определить результат успеха, пустое состояние, ошибку и повторную попытку.

## 3. Типографика и масштабирование

- Основной текст: целевой диапазон 16–18 CSS px для обычного чтения; вспомогательный текст не должен нести единственную важную инструкцию.
- Подписи полей — видимые и связанные с элементом через `label` / `for`; placeholder не заменяет подпись.
- Использовать общую шкалу заголовков, строк, межстрочных интервалов и отступов. Не задавать размеры локально без необходимости.
- Макет должен перестраиваться при увеличении масштаба до 400% без потери действий и без горизонтальной прокрутки основного текста, где это применимо по WCAG.
- Не фиксировать ширину текстовой кнопки так, чтобы надпись обрезалась. Допускать перенос и рост высоты.
- Текст должен оставаться выделяемым, копируемым и читаемым средствами доступности.

## 4. Кнопки и ссылки

### 4.1. Семантика

- `button` — выполнить действие, отправить форму, изменить состояние или открыть интерфейсный элемент.
- `a` — перейти на страницу, внешний ресурс или якорь.
- Кнопка отправки формы имеет `type="submit"`; остальные кнопки внутри формы — явный `type="button"`, чтобы избежать случайной отправки.
- Ссылки не должны иметь пустой или фиктивный `href="#" `, если переход не реализован как настоящий якорь.

### 4.2. Размер и поведение по тексту

- Кнопка растёт по содержимому: ширина определяется подписью и контекстом, а не единым жёстким значением.
- Базовый ориентир для обычной кнопки: высота не менее 44 CSS px, горизонтальные внутренние отступы около 12–16 px и вертикальные около 10–12 px.
- Критерий WCAG 2.2 AA для минимального размера цели — 24 × 24 CSS px с исключениями; 44 × 44 px используется здесь как более удобная проектная цель для основных интерактивных действий.
- Базовые свойства: `inline-flex`, `align-items:center`, `justify-content:center`, `max-width:100%`, `min-width:0`, `line-height:1.25`, `text-align:center`, `overflow-wrap:anywhere`.
- Не использовать `white-space:nowrap` для длинных русских надписей. Допускать перенос строки и увеличение высоты.
- Не растягивать все кнопки на всю ширину автоматически. `width:100%` — для мобильных форм или когда это помогает основному действию.
- Иконка не заменяет понятный текст, кроме действительно знакомых компактных элементов с доступным именем.
- Основное действие визуально заметнее вторичных. Обычно одно главное действие на контекст; несколько равноправных действий допустимы, если они действительно независимы и это понятно пользователю.
- На мобильном экране группы связанных действий могут складываться вертикально. Не уменьшать шрифт кнопки, чтобы втиснуть её в строку.

### 4.3. Состояния

Каждый интерактивный компонент должен иметь различимые состояния: обычное, наведение (для устройств с наведением), фокус клавиатуры, нажатие, отключено, загрузка/выполнение и ошибка/успех там, где применимо. Цвет не должен быть единственным носителем смысла.

## 5. Формы и клавиатура

- Для однострочного поля внутри корректной HTML-формы Enter должен запускать то же основное действие, что и кнопка отправки.
- Для каждой формы проверить: Enter, клик по кнопке, пустое значение, пробелы по краям, ошибку валидации, отсутствие результатов и повторный поиск.
- Обработчик `submit` должен вызывать реальную функцию, предотвращать стандартную отправку только при наличии управляемого клиентского сценария и показывать видимый результат.
- Результат поиска не должен оставаться ниже экрана без уведомления: после Enter нужно показать статус и прокрутить к результатам, если они находятся вне видимой области.
- Для сообщений о результате использовать доступную область, например `aria-live="polite"`; не сообщать об успехе до завершения действия.
- Поиск по названию документа и подбор по описанию ситуации — разные режимы с понятными названиями и самостоятельными результатами.
- Текст запроса нормализуется предсказуемо: регистр, пробелы, `ё/е`; для поиска по названию не подменять совпадение по заголовку произвольным совпадением по описанию, если интерфейс заявляет точный поиск по названию.

## 6. Сетка, ширина и адаптивность

- Использовать CSS Grid / Flexbox с `minmax(0, 1fr)`, `min-width:0` и явными адаптивными переходами, чтобы длинный текст не расширял колонку.
- Контейнеры, панели, поля и кнопки не должны выходить за ширину родителя.
- Ширина страницы и колонок должна соответствовать задаче; редактор документа получает больше места, чем вспомогательная навигация.
- На узком экране инструменты переходят в раскрываемые панели или последовательные секции, а не сжимают редактор до нечитаемой ширины.
- Не использовать позиционирование, которое перекрывает результаты поиска, кнопки, поля или фокус клавиатуры.
- При каждом изменении проверять соседние элементы, состояния прокрутки, мобильную ширину и увеличение масштаба.

## 7. Дубли кнопок и ссылок

Перед удалением дубля сравнить не только текст, но и назначение, URL, контекст и состояние:

1. Нормализовать путь (учесть завершающий слеш и query-параметры, если они меняют режим).
2. Сгруппировать одинаковые действия на каждой странице.
3. Оставить одну основную точку доступа в контексте и убрать повторения без дополнительной пользы.
4. Сохранять повторный доступ, если он нужен в другом контексте — например, постоянная навигация и действие внутри пустого рабочего пространства.
5. Не удалять полезный короткий путь до действия, не проверив пользовательский сценарий.
6. Для каждой оставшейся ссылки подтвердить существование маршрута или корректность внешнего адреса. Якорь должен существовать в текущем документе.

## 8. Проверки при изменениях

Минимальный набор для затронутого сценария:

- статическая проверка HTML-идентификаторов, путей к CSS/JS и локальных ссылок;
- проверка JavaScript-синтаксиса доступным инструментом;
- тестирование Enter и клика по основной кнопке;
- тесты точного названия, частичного названия, `ё/е`, лишних пробелов, пустого запроса и отсутствия совпадений;
- проверка, что подбор по ситуации не фильтруется поиском по названию и наоборот;
- проверка статуса, видимости результата, клавиатурного фокуса и прокрутки;
- проверка широкой и мобильной ширины, длинных подписей и масштаба;
- повторное чтение сохранённых файлов и проверка diff;
- после публикации — проверка опубликованной версии и фактических пользовательских сценариев. Успешный workflow сам по себе не доказывает, что интерфейс работает.

## 9. Приёмка и статус доказательств

Для каждого сценария отдельно указывать один из статусов: **работает и проверено**, **исправлено в коде, исполнение не проверено**, **ошибка подтверждена**, **маршрут отсутствует**, **не проверено**. Не объявлять весь сайт проверенным на основании проверки одной страницы или анализа исходного кода.

## 10. Порядок применения

Новый стандарт применяется к новым страницам сразу. Существующие страницы приводятся к нему поэтапно: сначала критические ошибки и потерянные действия, затем маршруты и навигация, затем повторяющиеся компоненты и визуальная унификация. Большой редизайн не должен маскировать критические функциональные дефекты.
