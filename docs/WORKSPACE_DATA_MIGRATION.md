# text2me — аудит связей рабочего пространства и переход к серверной БД

**Статус:** архитектурный план. Серверная база, аккаунты и синхронизация пока не реализованы. Текущий сайт на GitHub Pages — статическое приложение; данные рабочего пространства сейчас хранятся в браузере.

## 1. Что обнаружено в текущей модели

Текущий локальный источник истины — `text2me.workspace.core.v1`, с миграцией из старых ключей:

- `text2me.dashboard.v1` — дела, документы, задачи и события рабочего стола;
- `text2me.crm.workspace.v1` — CRM-записи и журнал;
- `text2me.space.v1` — сохранённые документы и шаблоны;
- `text2me.drafts.v1` — черновики.

Основные проблемы, которые нужно учитывать до серверной синхронизации:

1. Ранее CRM связывал дела и контакты преимущественно строками имён; одинаковые имена и переименование могли разрушать связь.
2. Не все формы проверяли, что переданный `caseId`, `documentId` или `contactId` действительно существует.
3. Сущности календаря и задач могли хранить ссылку на документ по ID записи библиотеки, а не по ID документа рабочего пространства.
4. Автоматическое создание дела для библиотечного документа могло повторно создавать дело после его удаления.
5. Удаление CRM-записи документа могло удалять исходный элемент из `text2me.space.v1`, хотя пользователь удалял только рабочую запись.
6. Схема не описывала контакты и часть связей задач/событий.
7. Разные страницы синхронизируют данные через несколько адаптеров; каждый адаптер должен соблюдать одинаковые инварианты.

В этой ветке добавлены проверки отношений и исправления локальной модели. Это не означает, что серверная синхронизация уже существует.

## 2. Каноническая модель

Идентификаторы должны быть стабильными ID, а не названиями или индексами массива.

| Сущность | Основные поля | Связи |
|---|---|---|
| `cases` | `id`, `title`, `status`, `timestamps` | много контактов; много документов, задач и событий |
| `contacts` | `id`, `name`, `email`, `phone`, `organization` | много дел, документов, задач и событий |
| `documents` | `id`, `title`, `content`, `status`, `libraryId` | одно дело; много контактов; задачи/события могут ссылаться на документ |
| `tasks` | `id`, `title`, `status`, `due`, `priority` | необязательное дело, документ, несколько контактов |
| `events` | `id`, `title`, `date` | необязательное дело, документ, несколько контактов |
| `activity` | `id`, `action`, `at` | необязательная сущность и её ID |

На сервере связи «многие ко многим» следует хранить в отдельных таблицах, а не в JSON-массивах:

- `case_contacts(case_id, contact_id)`
- `document_contacts(document_id, contact_id)`
- `task_contacts(task_id, contact_id)`
- `event_contacts(event_id, contact_id)`

Поля `case_id` и `document_id` должны иметь внешние ключи. ID источника библиотеки (сейчас `libraryId`) нельзя путать с ID сущности рабочего пространства.

## 3. Обязательные инварианты

1. У каждой сущности уникальный стабильный ID и явный владелец `user_id` на сервере.
2. `caseId` указывает на существующее дело либо равен `null`.
3. `documentId` у задачи/события указывает на существующий документ рабочего пространства либо равен `null`; ID библиотечной записи не принимается как ID документа без явного преобразования.
4. Каждый ID в `contactIds` указывает на существующий контакт. Дубликаты ID запрещены.
5. Удаление контакта удаляет его связи из всех join-таблиц.
6. Удаление дела не должно автоматически удалять документы или контакты; связь очищается либо действие блокируется с понятным подтверждением.
7. Удаление документа рабочего пространства не должно молча удалять исходный файл/запись из библиотеки. Удаление источника — отдельное явное действие.
8. Инициализация связей для старых записей должна быть идемпотентной и не воссоздавать удалённые дела.
9. Изменения связанных сущностей выполняются в одной серверной транзакции.
10. При конфликте синхронизации нельзя молча перезаписывать более свежие данные.

## 4. Предлагаемая серверная архитектура

- **Frontend:** статические страницы остаются на GitHub Pages; в них нет секретов и прямого подключения к БД.
- **API:** отдельный HTTPS backend с проверкой прав на каждый объект и операцию.
- **База:** PostgreSQL как основное реляционное хранилище.
- **Файлы:** отдельное объектное хранилище с приватными объектами и ссылками ограниченного срока; метаданные и связи хранятся в PostgreSQL.
- **Аутентификация:** пользователь входит в свой аккаунт; сервер получает владельца из проверенной сессии/токена, а не из переданного клиентом `user_id`.
- **Авторизация:** все запросы фильтруются по владельцу; нельзя получить объект другого пользователя, подставив ID.
- **История:** аудит действий с сущностью, временем, пользователем и результатом; не записывать в логи содержимое документов и лишние персональные данные.
- **Версионирование:** `version` или `updated_at` с optimistic concurrency; API возвращает конфликт, если запись уже изменилась.
- **Идемпотентность:** операции синхронизации и импорта имеют ключ идемпотентности.
- **Резервные копии:** автоматические зашифрованные backups, проверка восстановления и документированный RPO/RTO.

### Черновой API

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/v1/me/workspace` | метаданные рабочего пространства и версия схемы |
| GET/POST | `/api/v1/cases` | список и создание дел |
| GET/PATCH/DELETE | `/api/v1/cases/{id}` | чтение, изменение и удаление дела |
| GET/POST | `/api/v1/contacts` | контакты |
| GET/POST | `/api/v1/documents` | документы и ссылки на файлы |
| GET/POST | `/api/v1/tasks` | задачи |
| GET/POST | `/api/v1/events` | календарные события |
| POST | `/api/v1/sync/preview` | проверка локального экспорта без записи |
| POST | `/api/v1/sync/commit` | подтверждённый импорт в серверную транзакцию |
| GET | `/api/v1/sync/{id}` | результат/статус операции синхронизации |

Это проект контракта, а не существующие endpoint-адреса.

## 5. План миграции без потери данных

1. **Стабилизировать локальную схему.** Зафиксировать поля, отношения, правила удаления и версию миграции. Запретить адаптерам создавать висячие ссылки.
2. **Экспорт и резервная копия.** Предоставить экспорт всего рабочего пространства в версионированный JSON. Перед миграцией автоматически предложить скачать копию.
3. **Backend и БД.** Создать таблицы, внешние ключи, join-таблицы, ограничения владельца, миграции SQL и тестовые данные.
4. **Аккаунт и авторизация.** Проверить создание сессии, восстановление доступа, завершение сессии, CSRF, rate limiting и изоляцию пользователей.
5. **Preview.** Прочитать локальные данные, проверить ссылки, дубликаты, отсутствующие ID и несовместимые поля; показать пользователю сводку до записи.
6. **Импорт в транзакции.** Сначала создать/сопоставить сущности, затем отношения. При ошибке откатить транзакцию целиком.
7. **Сверка.** Сравнить количество и контрольные суммы сущностей, контактов, документов, задач, событий и связей. Не удалять локальную копию.
8. **Двухрежимная проверка.** До отключения локального режима провести тестовую синхронизацию и проверить конфликтные изменения, повтор запроса и восстановление.
9. **Явное переключение.** Переводить аккаунт на сервер только после подтверждения пользователя и успешной сверки.
10. **Откат.** Сохранять локальный экспорт и возможность возврата до завершения периода наблюдения. Не допускать двойной записи без определённого источника истины.

## 6. Персональные данные и размещение

Для российского запуска до выбора провайдера нужно отдельно проверить применимые требования к персональным данным. В частности, часть 5 статьи 18 Федерального закона № 152-ФЗ регулирует использование баз данных при сборе персональных данных граждан РФ и содержит исключения. Актуальная редакция и применимость исключений должны быть проверены юристом до выбора инфраструктуры: [текст статьи 18 в актуальной редакции](https://www.consultant.ru/document/Cons_doc_LAW_61801/cbf4e15b7c330f9372e876cdf2bc928bad7950ef/).

Практические требования к проектированию:

- выбрать и документально подтвердить место первичной записи/хранения данных;
- отдельно проверить географию основной БД, реплик, backups, объектного хранилища, логов и сервисов поддержки;
- определить цели, минимальный состав данных, сроки хранения, основания обработки и порядок удаления;
- подготовить политику обработки персональных данных, необходимые согласия/уведомления и договоры с обработчиками, если они требуются;
- обеспечить шифрование при передаче и хранении, управление секретами, минимальные привилегии, журнал доступа, обновления и реагирование на инциденты;
- не отправлять данные из браузера на сервер автоматически; миграция запускается пользователем после входа и предварительного просмотра.

Этот раздел — технический чек-лист, а не юридическое заключение.

## 7. Критерии готовности серверной миграции

- [ ] Есть утверждённая схема SQL и воспроизводимые миграции.
- [ ] Все внешние ключи и правила удаления протестированы.
- [ ] API не допускает чтение/изменение чужих сущностей.
- [ ] Тесты проверяют повтор импорта, конфликты, частичный сбой и rollback.
- [ ] Экспорт/импорт восстанавливает данные и все связи.
- [ ] Проверены резервное копирование и реальное восстановление.
- [ ] Проверены место обработки данных и правовые требования.
- [ ] Пользователь явно подтверждает подключение и перенос данных.
- [ ] Локальная копия сохраняется до успешной сверки и подтверждённого переключения.
